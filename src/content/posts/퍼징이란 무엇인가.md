# 퍼징이란 무엇인가

이번에 버그바운티 공부하면서 퍼징이라는 개념을 제대로 정리해보고 싶어서 글을 써봤다. 솔직히 처음엔 그냥 "랜덤 입력 넣는 거 아냐?" 정도로만 알고 있었는데 파고들수록 생각보다 훨씬 깊은 분야였다.

---

## 퍼징이 뭔데?

**퍼징(Fuzzing)** 은 프로그램에 이상한 입력값을 엄청 많이 집어넣어서 크래시나 버그를 찾아내는 기법이다. 쉽게 말하면 "이 프로그램 뭘 넣으면 터질까?" 를 자동으로 탐색하는 것.

시작은 1988년으로 꽤 오래됐다. 바턴 밀러라는 교수가 Unix 유틸리티들에 무작위 문자를 넣어봤더니 프로그램 25~33%가 뻗어버렸다는 게 계기였다고 한다. 그때부터 퍼징이 보안 연구 분야에서 주목받기 시작했고, 지금은 구글, 마이크로소프트 같은 대기업들도 제품 배포 전에 퍼징을 필수로 돌린다.

퍼징으로 찾을 수 있는 취약점은 꽤 다양한데 주로 이런 것들이다.

- Buffer Overflow, Use-After-Free, Heap Corruption 같은 메모리 관련 버그
- Integer Overflow, Null Pointer Dereference
- Format String 취약점
- 특이한 입력에서 터지는 로직 에러

---

## 퍼징의 종류

### 블랙박스 퍼징

내부 구조 아무것도 모르고 그냥 입력/출력만 보면서 퍼징하는 방식이다. 소스코드 없어도 되니까 편하긴 한데 코드 커버리지가 낮아서 깊은 버그는 못 찾는 경우가 많다. 단순 랜덤 데이터 전송이나 네트워크 프로토콜 퍼징할 때 쓰는 방식.

### 화이트박스 퍼징

소스코드나 바이너리를 완전히 분석해서 심볼릭 실행으로 입력값을 만드는 방식이다. 이론상 모든 코드 경로를 탐색할 수 있는데, 실제로는 복잡한 프로그램에서 경로 폭발(path explosion) 문제가 터져서 현실적으로 쓰기가 어렵다. SAGE, KLEE 같은 도구들이 여기 해당한다.

### 그레이박스 퍼징 (지금 주류)

지금 퍼징 생태계에서 가장 많이 쓰이는 방식이다. 바이너리 계측을 통해 코드 커버리지 피드백을 받아서 새로운 경로를 탐색하는 입력값을 우선적으로 변이시키는 방식인데, 블랙박스보다 효율적이고 화이트박스보다 빠르다. AFL, AFL++, libFuzzer 같은 게 다 여기에 속한다.

동작 흐름을 대충 설명하면 이렇다:
1. 초기 시드 입력을 준비한다
2. 타겟 프로그램에 입력을 넣고 실행
3. 새로운 코드 경로가 탐색됐으면 시드 큐에 추가
4. 시드를 변이(bit flip, 블록 교체 등)시켜서 다시 2번으로

이 사이클을 계속 반복하면서 점점 더 깊은 코드 경로를 탐색한다.

### 뮤테이션 기반 vs 생성 기반

퍼징을 입력 생성 방식으로도 나눌 수 있다.

**뮤테이션 기반**은 기존 입력값을 변형하는 방식이고, **생성 기반**은 문법이나 스펙에 따라 새 입력을 처음부터 만드는 방식이다. AFL++은 뮤테이션 기반이고, Peach나 Boofuzz 같은 도구들은 생성 기반에 해당한다.

## 대표적인 퍼저들

### AFL++ (American Fuzzy Lop++)

> [https://github.com/AFLplusplus/AFLplusplus](https://github.com/AFLplusplus/AFLplusplus)

AFL은 Google의 Michal Zalewski가 만들었고, AFL++은 그걸 커뮤니티에서 개선한 버전이다. 퍼징 공부하면 무조건 먼저 만나게 되는 도구라고 생각하면 된다.

소스코드가 있으면 컴파일할 때 `afl-clang-fast` 같은 걸 써서 커버리지 추적 코드를 삽입하고, 소스코드 없이 바이너리만 있으면 QEMU 모드로 돌릴 수 있다 (대신 좀 느려진다).

AFL에서 AFL++로 오면서 추가된 게 꽤 있는데 주요한 건 이 정도다.

- **CmpLog**: 비교 연산을 로깅해서 매직 값이나 체크섬 같은 걸 알아서 처리해줌
- **Custom Mutator API**: 직접 변이 로직을 짜서 연결할 수 있음
- **LTO 계측**: 링크 타임 최적화 기반 계측으로 더 정확한 커버리지
- **MOpt**: 유전 알고리즘으로 변이 전략을 자동 최적화

기본 사용법은 이렇다.

```bash
# 소스코드 컴파일
CC=afl-clang-fast ./configure && make

# 퍼징 시작
afl-fuzz -i seeds/ -o output/ -- ./target @@
```

`@@` 자리에 퍼저가 생성한 입력 파일 경로가 들어간다.

### Jackalope

> [https://github.com/googleprojectzero/Jackalope](https://github.com/googleprojectzero/Jackalope)

Google Project Zero에서 만든 퍼저인데, AFL++과 다르게 **바이너리만 있어도 된다**는 게 핵심이다. Windows랑 macOS를 지원해서 클로즈드 소스 앱을 퍼징할 때 유용하다.

내부적으로 **Tinyinst** 라는 동적 바이너리 계측 라이브러리를 써서 실행 중에 커버리지를 수집한다. AFL++의 QEMU 모드랑 비슷한 개념인데 Windows/macOS에 훨씬 잘 맞게 설계되어 있다.

파일 입력 말고도 네트워크 소켓이나 공유 메모리로 입력을 전달하는 것도 지원해서 네트워크 서비스 퍼징도 가능하다. 확장성도 꽤 좋아서 커스텀 mutator 같은 것도 직접 붙일 수 있다.

AFL++이랑 비교하면 이런 느낌이다.

| | AFL++ | Jackalope |
|--|--|--|
| 주력 플랫폼 | Linux | Windows, macOS |
| 소스코드 | 있으면 좋음 | 없어도 됨 |
| 계측 방식 | 컴파일 타임 | 런타임(Tinyinst) |
| 생태계 | 훨씬 풍부 | 상대적으로 작음 |

---

### libFuzzer

LLVM 프로젝트에 포함된 퍼저로 Google이 만들었다. AFL++과 다르게 **인프로세스** 방식이라서 별도 프로세스 없이 타겟 함수를 반복 호출하는 방식이다. 그래서 속도가 엄청 빠르다.

단점은 소스코드가 반드시 필요하고, 퍼징할 함수를 직접 감싸는 코드를 짜야 한다는 거다. 형태는 이렇다.

```c
#include <stdint.h>
#include <stddef.h>

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    // 여기에 퍼징하고 싶은 코드를 넣는다
    parse_something(data, size);
    return 0;
}
```

ASan, UBSan이랑 같이 쓰면 버그 탐지율이 많이 올라간다.

### OSS-Fuzz

> [https://github.com/google/fuzzing](https://github.com/google/fuzzing/tree/master)

Google이 운영하는 오픈소스 자동 퍼징 서비스다. 오픈소스 프로젝트를 Google 클라우드에서 24/7로 퍼징해주는 개념인데, AFL++, libFuzzer, Honggfuzz 같은 여러 퍼저를 앙상블로 돌린다.

OpenSSL, curl, SQLite 같은 유명한 프로젝트들이 다 등록되어 있고, 크래시 발견하면 개발자한테 자동으로 보고도 해준다. 지금까지 발견한 취약점이 1만 건이 넘는다고 하니까 규모가 어마어마하다.

## 뭘 쓰면 될까?

상황마다 적합한 도구가 다르다.

- **Linux, 소스코드 있음** → AFL++ 또는 libFuzzer
- **Windows/macOS 클로즈드 바이너리** → Jackalope
- **빠른 인프로세스 퍼징** → libFuzzer
- **오픈소스 프로젝트 장기 퍼징** → OSS-Fuzz 등록

처음 시작이면 AFL++로 시작하는 게 자료도 많고 커뮤니티도 크니까 제일 무난하다고 생각한다.

---

## 마무리

퍼징을 처음 공부할 때는 그냥 랜덤 입력 뿌리는 거라고 생각했는데, 커버리지 피드백 기반의 그레이박스 퍼징이 얼마나 영리하게 동작하는지 알고 나서 좀 신기했다. 특히 AFL++이 CmpLog로 매직 값을 처리하는 방식이라든가, 유전 알고리즘으로 변이 전략을 자동 최적화하는 부분이 흥미로웠다.

버그바운티에서 퍼징을 실제로 써먹으려면 그냥 도구만 쓸 줄 아는 걸로는 부족하고, 타겟을 어떻게 harness 짜고 시드를 어떻게 준비하는지가 진짜 핵심인 것 같다. 다음엔 실제 타겟에 AFL++ 적용해보는 걸 해봐야겠다.
